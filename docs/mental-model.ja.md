# メンタルモデル

Dependency Palaceは3Dの髪の毛の絡まりではあってはいけません。依存関係グラフは「AがBに触れている」ことだけを示すものであり、コードの意味を示すものではありません。

理想的なイメージは、コードベースを理解した後に頭の中に現れる構造です：

- インターフェースは実装の上または前にある契約です。
- クラスは状態と振る舞いを持つ本体です。
- フィールドは所有している状態であり、それを含むクラスに近い位置にあります。
- メソッドは振る舞いのポートであり、クラスに近いが協力者に向かっています。
- 継承は垂直な構造関係です。
- 呼び出しや生成は振る舞いのルートです。
- インポートや型参照は弱い知識のルートです。
- パッケージやモジュールは単なるフォルダではなく、地区のようなものです。
- Haskellの型クラスは契約であり、インスタンスはその契約の実装です。
- Haskellの`data`/`newtype`/レコードは、フィールド型への構成エッジを持つデータ本体です。
- 関数の合成は見えるパイプラインであり、単なる呼び出しエッジではありません。

## 空間的ルール

焦点ビューは安定した意味的レイアウトを使用すべきです：

| コードの概念 | 3D配置 |
| --- | --- |
| 選択されたクラス | 中央の本体 |
| フィールド/プロパティ | 左側/下側の状態クラスター |
| メソッド/コンストラクタ | 右側/上側の振る舞いクラスター |
| 実装されたインターフェース | 上または前の契約面 |
| 基底クラス | 下または後ろの構造チェーン |
| 型クラスの制約 | 上または前の契約面 |
| 関数の合成 | 関数間の曲線の振る舞いパイプライン |
| 出ていく依存関係 | 右側 |
| 入ってくる依存関係 | 左側 |
| 遠いコンテキスト | 外側の軌道 |

## 視覚的ルール

| 概念 | 形状 |
| --- | --- |
| パッケージ | フラットな地区ブロック |
| クラス | ソリッドな本体 |
| インターフェース | 薄い契約面 |
| 列挙型 | 小さなファセットタワー |
| フィールド/プロパティ | 小さな状態粒子 |
| メソッド/コンストラクタ | 小さな振る舞いディスク |
| 外部型 | ニュートラルな多面体 |

## 製品ルール

最初に役立つスクリーンは次の質問に答えるべきです：

1. これは何の型か？
2. どんな状態を所有しているか？
3. どんな振る舞いを公開しているか？
4. どんな契約を満たしているか？
5. 誰を呼び出したり作成したりしているか？
6. 誰がそれに依存しているか？

もしビューが「エッジの数がいくつあるか」だけに答えているなら、それは十分ではありません。

右側パネルのSignalブロックはこれのコンパクトなテキスト版です。選択された記号に声を与えます：契約面、データ本体、振る舞いパイプライン、境界、アダプター、または状態保持者と、そのローカルな関係圧力です。

さまざまな比喩については [metaphors.md](metaphors.md) に記載されています。これらはスキンではなく、同じコード理解の異なる投影です。
